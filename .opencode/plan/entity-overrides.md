# План: оверрайд entity-полей при проксировании (гидратация)

Статус: **не реализовано**. Выбран вариант C из обсуждения: не резать запрос по
entity-полям, а исполнять ответ апстрима локально.

Связанные документы: `interceptors.md` (перехват пейлоада, независимый слой).

## Проблема

`--proxy-to` маршрутизирует только root-поля. `planRequest()` смотрит на
`override/queries|mutations/...`, локальную часть исполняет через `execute()`,
удалённую отправляет на апстрим, результаты склеиваются `mergeResults()` по
root-ключам.

Если root-поле ушло на апстрим, весь его sub-tree приходит из апстрима и
`override/entities/<Type>.ts` на него не действует: локальный execute для этого
поддерева не запускается.

Entity-поле — не ключ результата, а позиция в дереве (объект, элемент списка,
inline-фрагмент). «Разрезать» документ по нему (вариант A) напрямую нельзя:
локальной части нужен parent value из апстрима, а публичный `execute()` умеет
стартовать только с root-типа. Пришлось бы либо добавлять синтетические
root-поля, либо тянуть внутренности `graphql` (`collectFields`/`executeFields`)
и вручную повторять non-null bubbling, фрагменты, директивы и ошибки.

## Идея: гидратация

Не склеиваем два JSON, а исполняем **исходный клиентский документ локально**,
подставив данные апстрима как parent для proxied root-полей.

1. Апстрим получает только неоверрайднутое: root-поля без override и,
   best-effort, без entity-полей с override.
2. `data` из ответа кладётся в per-request контекст.
3. `execute()` по полному документу:
   - root-резолвер proxied-поля возвращает значение из контекста;
   - entity-поле с override резолвится из `override/entities/<Type>.ts`;
   - остальные entity-поля резолвятся `defaultFieldResolver` по JSON апстрима.

Entity-резолвер уже падает в `defaultFieldResolver(parent, ...)`, поэтому
upstream-JSON ведёт себя как обычный parent, а всю семантику GraphQL исполняет
`graphql-js`.

### Что получаем бесплатно

- алиасы, фрагменты, интерфейсы/юнионы, списки и вложенные списки;
- `@include/@skip` вычисляются один раз, локально;
- корректный non-null bubbling и `path` в ошибках;
- оверрайд получает настоящие `args` и `GraphQLResolveInfo`;
- объектнозначный оверрайд может вернуть сущность — её подвыборка исполнится
  локально;
- `mergeResults()`/`readUpstreamResult()` остаются только для чистого `proxy`
  (можно сохранить) и уходят из split-ветки.

### Ключевое свойство

Корректность **не зависит** от качества вырезания оверрайднутых полей из
удалённого документа: локальный execute всё равно вызовет оверрайд-резолвер и
проигнорирует лишние данные. Вырезание — только оптимизация трафика, поэтому
сложные случаи (абстрактные типы, директивы) можно оставлять как есть.

## Что считается entity-оверрайдом

- Файл `override/entities/<Type>.ts` (layout `override`, не `generated`).
- Named export с именем поля типа.
- `default` оверрайдом **не** считается: он есть у каждого сгенерированного
  файла и означает «значение типа», а не «поле».
- Существование файла само по себе ничего не включает — как и у root-полей.
- Для интерфейса/юниона действует правило генерации: мок описывает первый
  concrete-тип. Маршрутизация при исполнении идёт по concrete `__typename`;
  приоритет `override/entities/<Interface>.ts` против concrete-типа нужно
  зафиксировать (см. «Открытые вопросы»).

## Поток запроса

```
parse → planRequest
          ├─ local   → обычный execute (без изменений)
          ├─ proxy   → pass-through (без изменений)
          ├─ split   → текущая логика (нет выбранных entity-оверрайдов)
          └─ hydrate → forward (возможно, урезанный документ) → execute(полный документ, ctx)
```

`hydrate` выбирается, когда в поддеревьях **удалённых** root-полей есть хотя бы
одно поле с entity-оверрайдом. Если оверрайды есть только под локальными
root-полями, они и так применяются обычным локальным execute.

### План

```ts
export type RoutePlan =
  | { mode: "local" }
  | { mode: "proxy" }
  | { mode: "error"; error: string }
  | { mode: "split"; /* как сейчас */ }
  | {
      mode: "hydrate";
      remoteDocument: DocumentNode;
      remoteVariables: string[];
      remoteKeys: string[]; // response keys, ушедшие на апстрим
      order: string[];      // порядок root-ключей клиента
    };
```

Detection (`usesEntityOverride`) должна быть консервативной: сомнение → `true`.
Гидратация при ложном срабатывании корректна (лишний локальный execute), при
пропуске — оверрайд теряется.

### Контекст запроса

```ts
interface RequestContext {
  remoteRootKeys?: Set<string>;         // response keys, ушедшие на апстрим
  remoteRoots?: Map<string, unknown>;   // key → значение из data
  remoteValues?: WeakSet<object>;       // все объекты/массивы из апстрима
}
```

- Ключ — response key (`info.path.key` на корне), а не имя поля: алиасы должны
  работать.
- `remoteRoots` заполняется для **каждого** запланированного remote-ключа, даже
  если в ответе его нет (значение `undefined` → GraphQL трактует как `null`).
- `remoteValues` заполняется рекурсивным обходом значений апстрима. Нужен,
  чтобы `mockFallback` не выдумывал данные для полей, которых апстрим не вернул
  (ошибка/`null`): для remote-parent отсутствующее значение должно остаться
  `undefined` и всплыть по non-null правилам, а не превратиться в мок.
- Контекст per-request, схема не мутируется → конкурентность и хот-релоад в
  порядке.

### root-резолвер

```ts
return (parent, args, context, info) => {
  if (isRoot && context?.remoteRootKeys?.has(String(info.path.key))) {
    return context.remoteRoots?.get(String(info.path.key));
  }
  // ... текущая логика модулей
  const value = defaultFieldResolver(parent as never, args, context, info);
  if (value !== undefined) return value;
  if (!isRoot && isRemoteParent(parent, context)) return undefined;
  return mockFallback(field.type);
};
```

### Вырезание полей (оптимизация)

- Обход документа с учётом типа родителя (TypeInfo или ручной обход с
  type conditions).
- Резать поле можно только когда parent-тип точно известен и это object type с
  оверрайдом; для интерфейса/юниона без `__typename` — оставить как есть.
- Если selection set после вырезания опустел, добавить `__typename` (иначе
  документ невалиден).
- Пересчитать используемые фрагменты и переменные после вырезания (unused
  variable/fragment — ошибка валидации на большинстве серверов).
- Для абстрактных типов при желании — инжект `__typename` в удалённый документ;
  ответ локальному execute не мешает.

## Семантика и крайние случаи

| Случай | Поведение |
| --- | --- |
| Список/вложенные списки | Локальный execute обходит элементы, оверрайд применяется к каждому; длина списка — из апстрима. |
| Алиасы | Маршрутизация по типу, слияние — по response key; алиасы сохраняются. |
| Inline fragment / `... on Type` | Резолверы привязаны к типу, поэтому работает штатно; detection консервативна. |
| `@include`/`@skip` | Вычисляются локально; вырезание не должно менять результат (можно не резать поля с директивами). |
| Оверрайд вернул `null` в non-null поле | Ошибка всплывает до ближайшего nullable-предка, включая данные апстрима — штатная семантика `graphql-js`. |
| Ошибка апстрима на родителе (`data: null`) | `remoteRoots` отдаёт `null`, ошибки апстрима добавляются к ответу. |
| Апстрим не вернул ключ | `undefined` → `null` по GraphQL, `mockFallback` не подставляет мок. |
| Оверрайд вернул объект | Его подвыборка исполняется локально (моки/оверрайды), из апстрима эти поля не запрашиваются. |
| Оверрайд-функция с `info`/`args` | Получает настоящие `info`/`args` локального исполнения. |
| Поле оверрайднуто, но отсутствует в локальной схеме | Оверрайд не применяется (как у root-полей), поле остаётся за апстримом. |
| `--no-validate` | Работает как раньше: неизвестные локальной схеме поля отбрасываются. |
| Хот-релоад `override/entities/*` | Работает: `runtime.modules` читается в момент исполнения. |
| Порядок мутаций | Локальные и удалённые мутации одной операции по-прежнему не упорядочены между собой (апстрим отвечает до локального execute). |
| Подписки | Вне области: нет транспорта. |
| `extensions` | Явное правило: локальные поверх удалённых по ключу (как сейчас в `mergeResults`). |
| Ошибки | Локальные с полными путями, удалённые — как пришли; объединить и стабилизировать порядок по `order`. |

## Этапы

1. `overriddenEntities` в `mocks.ts` + юнит-тест загрузчика.
2. `hydrate` в `planRequest` без вырезания: remote-документ = текущий, исполняем
   полный документ с контекстом. Проверить, что split без entity-оверрайдов не
   изменился.
3. `usesEntityOverride` + включение `hydrate` по факту оверрайда.
4. Подавление `mockFallback` для remote-parent.
5. `stripEntityOverrides` как оптимизация (с тестом «стойкость к невырезанным
   полям»).
6. Документация: `README.md`, `AGENTS.md`, этот файл → «реализовано».

## Тесты

- оверрайд скалярного поля под proxied root → значение из `override/`;
- то же под списком и на нескольких уровнях вложенности;
- алиас и inline fragment на интерфейсе;
- `@include(if: false)` → оверрайд не применяется;
- несколько оверрайдов в одном selection set;
- оверрайд вернул объект → вложенные поля из мока;
- оверрайд вернул `null` в non-null → ошибка и bubbling до nullable-предка;
- апстрим вернул `null` для root → остальные поля работают, ошибки сохранены;
- поле отсутствует в ответе апстрима → `null`, не мок;
- смешанный запрос: один root локальный, другой proxied с entity-оверрайдом;
- полностью remote-запрос с entity-оверрайдом (нет локальных root-полей);
- локальный root без прокси → поведение не изменилось;
- `--no-validate`;
- хот-релоад `override/entities/<Type>.ts` подхватывается без рестарта.

## Не входит

- Оверрайд, который полностью заменяет сущность без запроса к апстриму
  (длина списка/существование объекта всё равно приходят из апстрима). Для
  этого есть root-override.
- Синтетические root-поля и deep import внутренностей `graphql`.
- Перехватчики пейлоада — см. `interceptors.md`; при реализации `after`
  применяется уже к гидратированному результату.

## Открытые вопросы

- Приоритет `override/entities/<Interface>.ts` против конкретного типа: брать
  concrete-тип, а интерфейс — только fallback (предложение), или наоборот?
- Нужен ли `mode`/директива, чтобы пометить entity-поле как «всегда локальное,
  даже если его нет в локальной схеме»?
- Всегда ли гидратировать split (и удалить `mergeResults`), или оставить
  быстрый путь без entity-оверрайдов?
- Сливать ли `extensions` по ключу или отдавать раздельно (`local`/`remote`)?
